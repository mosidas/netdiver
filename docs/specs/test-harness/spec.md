# test-harness — 仕様

## 1. 目的と背景

netdiver の MVP は 7 つの作業単位に分かれ、各単位の完了条件に「〜にテストがある」を含む(`docs/specs/roadmap.md`)。テストを書いて動かす基盤が無ければ、以降の単位はどれも完了を判定できない。

本単位は、GDScript のテストを記述・実行・判定する基盤を用意する。テストフレームワークに gdUnit4 v6.2.0 を採用し、`make test` の 1 コマンドで実行できるようにし、GitHub Actions の CI で pull request にチェックが付く状態にする。以降の単位は、この基盤の上にテストを追加するだけで済む。

## 2. スコープ

### 対象(やること)

- gdUnit4 v6.2.0 を取得して `addons/gdUnit4/` へ展開するスクリプト
- gdUnit4 のコマンドラインツールを包み、headless 実行の前提を整えて終了コードを正す実行スクリプト
- `make test` から実行する経路
- テストスイートの配置・命名・記述の規約
- GitHub Actions のワークフロー(Godot 4.7.1 の取得、`make test` の実行、レポートの保存)
- 上記が動くことを示すサンプルのテストスイート

### 対象外(やらないこと)

- 静的解析(gdlint / gdformat)の導入 — 理由: roadmap の本単位の範囲に含めていない。必要になった時点で別単位として追加する
- カバレッジの計測 — 理由: MVP の完了条件はカバレッジの数値ではなく、各単位の完了条件に挙げた振る舞いにテストがあることである
- C# のテスト — 理由: 技術方針は型注釈付き GDScript を基本とする(企画書 12.)
- ゲーム本体のテスト — 理由: 各単位(`foot-player` 以降)の範囲である。本単位は基盤とサンプルのみを置く
- Windows での実行 — 理由: 開発環境は macOS、CI は ubuntu-latest であり、動作を確かめられない環境の手順を仕様に含めない

## 3. 前提(未検証の賭け)

- **GitHub が自動生成するソースアーカイブ(`/archive/refs/tags/<tag>.zip`)は、再生成によってバイト列が変わりうる** — 検証方法: 同一タグのアーカイブを時期を空けて 2 回取得し、SHA-256 を比較する / 状態: 未検証。この前提のため、取得物の照合はアーカイブのチェックサムではなく、展開後の `plugin.cfg` の `version` で行う(§5.1)
- **gdUnit4 v6.2.0 は Godot 4.7.1 で動作する** — 検証方法: 一時プロジェクトに v6.2.0 を展開し、Godot 4.7.1 の headless でテストを実行する / 状態: **検証済み**(2026-08-11。純粋ロジックのテストと `CharacterBody2D` を物理フレームで動かすテストの両方が成功し、失敗時に終了コード 100 を返すことを確認した)
- **パースエラーを含むテストスイートだけを対象にした場合、gdUnit4 は終了コードを確実には反映せず、レポートも出力しない** — 検証方法: パースエラーを含むテストスイート 1 件だけを対象に、同一のコマンドを 3 回実行して終了コードとレポートの生成を比べる / 状態: **検証済み**(2026-08-12。`--continue -rd res://reports` を付けた同一実行で、終了コードが 105・0・0 と割れた。3 回ともレポートは出力されなかった)。このため、この経路の検出を終了コードに依存させず、レポートの `testcase` 件数で判定する(§5.2 副作用 6)
- **パースエラーを含むテストスイートが正常なテストスイートと混在する場合、gdUnit4 はレポートを出力したうえでクラッシュする** — 検証方法: 正常なスイート 1 件とパースエラーのスイート 1 件を同時に対象にして 3 回実行し、終了コードと `reports/` の生成有無・`testcase` 件数を見る / 状態: **検証済み**(2026-08-12。3 回とも終了コード 134、`results.xml` は生成され `testcase` は 0 件ではなかった。ログは `Abnormal exit with 105` の後に `handle_crash: Program crashed with signal 11` を出している)。この経路はレポートが出るため件数判定では検出できないが、終了コードが 0 でないため §5.2 副作用 5 の透過で失敗として表出する
- **`ubuntu-latest` で `curl` と `unzip` が使える** — 検証方法: CI の初回実行で確認する / 状態: 未検証
- **本リポジトリは headless でインポートできる** — 検証方法: `godot --headless --import --path .` を実行する / 状態: **検証済み**(2026-08-11。AsepriteWizard を有効にしたまま 2.7 秒、エラーなしで完了した)

## 4. 用語定義

| 用語 | 定義 |
| ---- | ---- |
| テストスイート | `GdUnitTestSuite` を継承した 1 つの GDScript ファイル。複数のテストケースを持つ |
| テストケース | テストスイート内の `test_` で始まるメソッド 1 つ |
| クラスキャッシュ | Godot が `class_name` の宣言を索引した `.godot/global_script_class_cache.cfg`。これが無いと `class_name` で宣言された型を実行時に解決できない |
| 取得スクリプト | gdUnit4 をダウンロードして `addons/gdUnit4/` へ展開する `scripts/fetch_gdunit4.sh` |
| 実行スクリプト | gdUnit4 のコマンドラインツールを包む `scripts/run_tests.sh` |

## 5. 公開インターフェース(API)

### 5.1 取得スクリプト `scripts/fetch_gdunit4.sh`

- **定義**: `scripts/fetch_gdunit4.sh`(引数なし)
- **入力**: なし。取得する版はスクリプト内の変数 `GDUNIT4_VERSION` で定義する。値は `v` を含まない形式(例: `6.2.0`)とし、`plugin.cfg` の `version` フィールドと直接比較できるようにする。取得 URL のタグ名は `v${GDUNIT4_VERSION}` として組み立てる
- **版の定義箇所の限定**: **実行に関与する成果物(取得スクリプト以外のスクリプト・`Makefile`・CI のワークフロー・`docs/testing.md`)に版の値を書かない**。本 spec.md は実装完了で凍結される中間生成物であり実行に関与しないため、この制限の対象外とする(§1・§2・§8 の版の記載は、検証を行った時点の記録である)
- **出力**: `addons/gdUnit4/` 以下に gdUnit4 の一式。標準出力に取得の有無と版
- **事前条件**: `curl` と `unzip` が PATH にある。ネットワークで `https://github.com/godot-gdunit-labs/gdUnit4` に到達できる
- **プロジェクト設定への影響**: `project.godot` の `editor_plugins` に gdUnit4 のプラグインを追加しない。`addons/gdUnit4/` は取得前には存在しないため(§6.4)、有効なプラグインとして列挙するとクローン直後のエディタ起動が警告を出す。コマンドラインからのテスト実行はプラグインの有効化を要求しない(実機で確認済み)
- **事後条件**: `addons/gdUnit4/plugin.cfg` が存在し、その `version` の値が `GDUNIT4_VERSION` と一致する
- **冪等性**: 実行前に `addons/gdUnit4/plugin.cfg` の `version` が `GDUNIT4_VERSION` と一致していれば、ダウンロードを行わず終了コード 0 で終わる
- **エラー**:

  | 条件 | 表出 |
  | ---- | ---- |
  | `curl` または `unzip` が無い | 標準エラーに不足しているコマンド名を出し、終了コード 1 |
  | ダウンロードに失敗した | 標準エラーに URL と HTTP ステータスを出し、終了コード 1 |
  | 展開後の `plugin.cfg` の `version` が `GDUNIT4_VERSION` と一致しない | 標準エラーに期待した版と実際の版を出し、終了コード 1 |

- **既存ディレクトリの置き換え**: `addons/gdUnit4/plugin.cfg` が存在し、その `version` が `GDUNIT4_VERSION` と一致しない場合に限り、`addons/gdUnit4/` を削除して取得し直す。削除は、そのディレクトリに `plugin.cfg` があり `name="gdUnit4"` を含むことを確認してから行う(誤ったパスを消さないため)

### 5.2 実行スクリプト `scripts/run_tests.sh`

- **定義**: `scripts/run_tests.sh [<テストのパス>]`
- **入力**: 第 1 引数にテストのパス(`res://` 形式)。省略時は `res://tests`
- **出力**: 標準出力に gdUnit4 の実行結果。`reports/` 以下にレポート(§6.3)
- **事前条件**: 環境変数 `GODOT_BIN` に Godot の実行ファイルのパスが設定されているか、`godot` が PATH にある。エディタ版のビルドであること(`--script` と `--import` はエディタ版でのみ使える)。`timeout` が PATH にある(macOS の標準構成には含まれないため、Homebrew の `coreutils` で入れる。本開発環境では `/opt/homebrew/bin/timeout` に存在することを確認済み)
- **事後条件**: 終了コード 0 は「**1 件以上のテストケースが実行され、そのすべてが成功した**」ことを意味する。それ以外はすべて非ゼロ
- **副作用**:
  1. `scripts/fetch_gdunit4.sh` を**毎回呼ぶ**。ダウンロードするかどうかは取得スクリプトが §5.1 の冪等性に従って判断する(版が一致していればダウンロードしない)。条件付きで呼ぶ形にすると、旧版が展開済みのローカル環境で版の不一致を検出できない
  2. `.godot/global_script_class_cache.cfg` が無ければ `--headless --import` を実行してクラスキャッシュを生成する
  3. gdUnit4 を実行する**前に** `reports/` を削除する。前回の実行が残したレポートを次回の判定材料にしないため(副作用 6 は「レポートが出ていない」ことを失敗の根拠にするので、古いレポートが残っていると探索エラーを検出できない)
  4. gdUnit4 のコマンドラインツールを `--headless --ignoreHeadlessMode --continue` と `-rd res://reports` を付けて実行する
  5. gdUnit4 の終了コードが 0 でなければ、その値をそのまま返して終わる
  6. gdUnit4 の終了コードが 0 の場合に限り、`reports/` 直下で連番が最大の `report_<連番>/results.xml` を読み、`testcase` 要素の件数を数える。`results.xml` が存在しないか件数が 0 なら、その旨を標準エラーへ出力して終了コード 1 とする(§7 Requirement 4.2 の判定材料)
  7. 全体を 120 秒のタイムアウトで包む
- **エラー**(終了コードの一覧):

  | コード | 意味 | 出所 |
  | -----: | ---- | ---- |
  | 0 | 1 件以上のテストケースが実行され全成功 | gdUnit4 |
  | 1 | 実行スクリプト自身のエラー(`GODOT_BIN` も `godot` も無い・`timeout` が無い・取得スクリプトの失敗・インポートの失敗・**gdUnit4 が 0 を返したが `results.xml` が無いか `testcase` が 0 件**) | 実行スクリプト |
  | 100 | テストの失敗またはテスト内の実行時エラー | gdUnit4 |
  | 101 | テストの警告 | gdUnit4 |
  | 103 | headless の拒否(`--ignoreHeadlessMode` を常に渡すため発生しない) | gdUnit4 |
  | 104 | 対応外の Godot バージョン | gdUnit4 |
  | 105 | テストの探索中にスクリプトエラー(パースエラー等) | gdUnit4 |
  | 124 | 120 秒のタイムアウト | `timeout` |
  | 134 | 探索中のスクリプトエラーが正常なテストスイートと混在したときのクラッシュ | gdUnit4 |

  0〜105 の値は gdUnit4 のソース `addons/gdUnit4/src/core/runners/GdUnitTestSessionRunner.gd` の定数(`RETURN_SUCCESS` = 0 / `RETURN_ERROR` = 100 / `RETURN_WARNING` = 101 / `RETURN_ERROR_HEADLESS_NOT_SUPPORTED` = 103 / `RETURN_ERROR_GODOT_VERSION_NOT_SUPPORTED` = 104 / `RETURN_ERROR_SCRIPT_ERRORS_DETECTED` = 105)による。134 は定数ではなく、プロセスがシグナルで終了した結果である(§3 の検証済みの前提)。

  gdUnit4 が返した終了コードは、副作用 6 の判定に該当する場合を除いて書き換えずそのまま返す。実行スクリプトが独自に判定するのは、上表の 1 に挙げた条件だけとする。**105 は gdUnit4 がプロセスの終了コードへ確実には反映しない**(同一の入力で 105 と 0 が混在することを実機で確認した。§3)。そのため、パースエラーの検出は 105 に依存しない。

### 5.3 Makefile ターゲット `make test`

- **定義**: `make test` / `make test TESTS=<テストのパス>`
- **入力**: 変数 `TESTS`(省略時は `res://tests`)。変数名に `PATH` を使わない(make が環境変数 `PATH` を上書きし、以降のコマンドの解決を壊すため)
- **事前条件**: 5.2 と同じ
- **事後条件**: `scripts/run_tests.sh` の終了コードをそのまま `make` の終了コードとする
- **既存ターゲットとの関係**: 既定ターゲット `all`(Aseprite からのスプライト生成)に依存しない。テストの実行に Aseprite を要求しない
- **エラー**: 5.2 の終了コードがそのまま伝わる

### 5.4 テストスイートの記述規約

テストを書く側が守る契約。実装ではなく規約であり、`docs/testing.md` に正本を置く。

- **定義**:

  ```gdscript
  # tests/<実装のディレクトリ構成を写したパス>/<対象>_test.gd
  extends GdUnitTestSuite

  func before_test() -> void: ...   # 各テストケースの前に実行される
  func after_test() -> void: ...    # 各テストケースの後に実行される

  func test_<検証する振る舞い>() -> void:
      assert_int(actual).is_equal(expected)
  ```

- **ファイル名**: 接尾辞 `_test.gd`。実装 `src/player/player.gd` に対するテストは `tests/player/player_test.gd`
- **テストケース名**: 接頭辞 `test_`
- **アサーション**: gdUnit4 が提供する `assert_*` 系(`assert_int` / `assert_float` / `assert_str` / `assert_bool` / `assert_array` / `assert_dict` / `assert_object` / `assert_vector` / `assert_signal` 等)を使う。**独自のアサーション関数を定義しない**
- **ノードの後始末**: `add_child(node)` したノードは `auto_free(node)` を対にする(gdUnit4 が解放漏れを orphan として報告するため)
- **物理フレームの進行**: `await await_millis(<ミリ秒>)` で待つ
- **禁止事項**: `Input` / `InputEvent` を経由する入力のシミュレーションをテストに書かない。headless では `InputEvent` がエンジンを通らず、テストが常に成立してしまう。入力に依存する振る舞いは、入力の読み取りとロジックを分けてロジック側を直接呼んで検証する
- **エラー**: 規約に反したテストの扱いは gdUnit4 の判定に従う。実行時エラーは終了コード 100 として表出する。パースエラーは探索時に検出され、gdUnit4 が 105 を返した回は 105、0 を返した回は §5.2 副作用 6 の件数判定により 1 として表出する(105 が確実には伝わらないため。§3)

### 5.5 CI ワークフロー `.github/workflows/test.yml`

- **定義**: GitHub Actions のワークフロー。トリガーは `pull_request` と、`main` への `push`
- **実行環境**: `ubuntu-latest`
- **Godot の入手**: 公式リリースの Linux ビルドを URL 固定でダウンロードする。URL は `https://github.com/godotengine/godot/releases/download/4.7.1-stable/Godot_v4.7.1-stable_linux.x86_64.zip`(バージョンはローカルと同じ 4.7.1)。サードパーティの action を使わない
- **手順**: チェックアウト → Godot の取得と `GODOT_BIN` の設定 → `make test`
- **事後条件**: `make test` の終了コードが 0 のときだけジョブが成功する
- **成果物**: `reports/` を `actions/upload-artifact` でアップロードする。保存期間は 14 日。テストの成否にかかわらずアップロードする
- **エラー**: Godot のダウンロードに失敗した場合、ジョブは失敗する(テストの失敗と区別できるよう、ステップを分ける)

## 6. データ構造

### 6.1 gdUnit4 の版指定

- **定義**: `scripts/fetch_gdunit4.sh` 内の変数 `GDUNIT4_VERSION`(文字列。`v` を含まない形式)
- **不変条件**: 実行に関与する成果物のうち、この変数だけが版の値を持つ。`docs/testing.md`・CI のワークフロー・`Makefile` は値を持たず、取得スクリプトを呼ぶ
- **照合の所在**: 取得したものが指定の版であることの判定は取得スクリプトが行う。判定の材料は `addons/gdUnit4/plugin.cfg` の `version` フィールドである
- **版を上げる手続き**: `GDUNIT4_VERSION` を書き換えて `make test` を実行する。実行スクリプトが取得スクリプトを毎回呼ぶため(§5.2 副作用 1)、取得スクリプトが版の不一致を検出し、`addons/gdUnit4/` を取得し直す

### 6.2 テストの配置

```
tests/
  <実装のディレクトリ構成を写したパス>/
    <対象>_test.gd
```

- **不変条件**: テストスイートは `tests/` 以下にのみ置く。実装ファイルと同じディレクトリに置かない
- **この配置を選ぶ理由**: gdUnit4 はファイル名でも配置でもテストの発見範囲を制約しない(コマンドラインに渡したパスを走査する)。制約があるのはエディタ機能「Create Test」の生成先(既定は実装の隣の `test/` サブフォルダ)とファイル名(接尾辞 `_test.gd`)だけである。ファイル名は生成機能と手書きで割れないよう gdUnit4 に合わせ、配置は実装と分離してエクスポート時の除外を 1 ディレクトリの指定で済ませる

### 6.3 レポート

- **形式**: gdUnit4 が `reports/report_<連番>/` に `results.xml`(JUnit 形式)と `index.html` を出力する
- **不変条件**: `reports/` は生成物であり、リポジトリに含めない

### 6.4 リポジトリに含めないファイル

`.gitignore` に次を追加する。

| パターン | 理由 |
| -------- | ---- |
| `addons/gdUnit4/` | 取得スクリプトが再現できる生成物。516 ファイル・1.7MB を履歴に入れない。`addons/` には AsepriteWizard がコミット済みのため、`addons/` 全体ではなくこのディレクトリだけを対象にする |
| `reports/` | テスト実行のたびに生成される |

## 7. 振る舞い(受け入れ基準)

### Requirement 1: gdUnit4 の導入と版の照合

**対象**: §5.1 取得スクリプト / §6.1 gdUnit4 の版指定

**受け入れ基準**:

1.1. システムは、実行に関与する成果物(取得スクリプト以外のスクリプト・`Makefile`・CI のワークフロー・`docs/testing.md`)に gdUnit4 の版の値を書かず、`scripts/fetch_gdunit4.sh` の変数 `GDUNIT4_VERSION` ただ 1 箇所で定義しなければならない。(常時)
1.2. `addons/gdUnit4/` が存在しない状態で取得スクリプトが実行されたとき、システムは gdUnit4 を取得して `addons/gdUnit4/` へ展開しなければならない。(イベント)
1.3. `addons/gdUnit4/plugin.cfg` の `version` が `GDUNIT4_VERSION` と一致する状態で取得スクリプトが実行されたとき、システムはダウンロードを行わず終了コード 0 で終了しなければならない。(イベント)
1.4. `addons/gdUnit4/plugin.cfg` の `version` が `GDUNIT4_VERSION` と一致しない場合、システムは `addons/gdUnit4/` を削除して取得し直さなければならない。(異常系)
1.5. 展開後の `addons/gdUnit4/plugin.cfg` の `version` が `GDUNIT4_VERSION` と一致しない場合、システムは期待した版と実際の版を標準エラーへ出力し、終了コード 1 で終了しなければならない。(異常系)
1.6. `curl` または `unzip` が PATH に無い場合、システムは不足しているコマンド名を標準エラーへ出力し、終了コード 1 で終了しなければならない。(異常系)
1.7. ダウンロードに失敗した場合、システムは URL と HTTP ステータスを標準エラーへ出力し、終了コード 1 で終了しなければならない。(異常系)
1.8. システムは、`project.godot` の `editor_plugins` に gdUnit4 のプラグインを追加してはならない。(常時)
1.9. システムは、`GDUNIT4_VERSION` の値を `v` を含まない形式で保持し、取得 URL のタグ名を `v${GDUNIT4_VERSION}` として組み立てなければならない。(常時)

### Requirement 2: テスト実行の入口

**対象**: §5.3 Makefile ターゲット `make test` / §5.2 実行スクリプト

**受け入れ基準**:

2.1. `make test` が実行されたとき、システムは `res://tests` 以下のテストスイートをすべて実行しなければならない。(イベント)
2.2. `make test TESTS=<パス>` が実行されたとき、システムは指定されたパス以下のテストスイートだけを実行しなければならない。(イベント)
2.3. システムは、`scripts/run_tests.sh` の終了コードを `make test` の終了コードとしなければならない。(常時)
2.4. システムは、`make test` の実行に Aseprite を要求してはならない。(常時)
2.5. `make test` が実行されたとき、システムはテストの実行前に `scripts/fetch_gdunit4.sh` を呼ばなければならない。(イベント)
2.6. `make test` が実行されたとき、システムはテストの実行前にクラスキャッシュの生成(Requirement 3)を済ませなければならない。(イベント)

### Requirement 3: headless 実行の前提整備

**対象**: §5.2 実行スクリプト

**受け入れ基準**:

3.1. `.godot/global_script_class_cache.cfg` が存在しない状態でテストが実行されたとき、システムは `--headless --import` を実行してクラスキャッシュを生成しなければならない。(イベント)
3.2. システムは、gdUnit4 のコマンドラインツールに `--ignoreHeadlessMode` を常に渡さなければならない。(常時)
3.3. システムは、gdUnit4 のコマンドラインツールに `--continue` を常に渡し、最初の失敗で中断せず全テストケースを実行しなければならない。(常時)
3.4. 環境変数 `GODOT_BIN` が設定されておらず `godot` も PATH に無い場合、システムはその旨を標準エラーへ出力し、終了コード 1 で終了しなければならない。(異常系)
3.5. クラスキャッシュの生成が失敗した場合、システムはテストを実行せず、終了コード 1 で終了しなければならない。(異常系)
3.6. `timeout` が PATH に無い場合、システムはその旨と入手方法(macOS では Homebrew の `coreutils`)を標準エラーへ出力し、テストを実行せず終了コード 1 で終了しなければならない。(異常系)

### Requirement 4: 実行結果の終了コード

**対象**: §5.2 実行スクリプト

**受け入れ基準**:

4.1. 1 件以上のテストケースが実行され、そのすべてが成功したとき、システムは終了コード 0 を返さなければならない。(イベント)
4.2. gdUnit4 が終了コード 0 を返し、かつ `reports/` 直下で連番が最大の `report_<連番>/results.xml` が存在しないか、その `testcase` 要素が 0 件の場合、システムはその旨を標準エラーへ出力し、終了コード 1 を返さなければならない。(異常系)
4.3. テストケースが 1 件以上失敗した場合、システムは gdUnit4 が返した終了コード 100 をそのまま返さなければならない。(異常系)
4.4. gdUnit4 が 0 以外の終了コードを返した場合、システムは件数の判定を行わず、その値をそのまま返さなければならない。(異常系)
4.5. 4.2 に該当する場合を除き、システムは gdUnit4 が返した終了コードを書き換えてはならない。(常時)
4.6. テストの探索中にスクリプトエラーが検出され、gdUnit4 が終了コード 0 を返した場合、システムは 4.2 の判定により終了コード 1 を返さなければならない。(異常系)

### Requirement 5: テストスイートの記述規約

**対象**: §5.4 テストスイートの記述規約 / §6.2 テストの配置

**受け入れ基準**:

5.1. システムは、テストスイートの配置・命名・アサーション・後始末・禁止事項を `docs/testing.md` に記載しなければならない。(常時)
5.2. システムは、純粋なロジックを検証するサンプルのテストスイートを `tests/` 以下に 1 つ以上持たなければならない。(常時)
5.3. システムは、ノードをシーンツリーに追加して物理フレームを進める統合テストのサンプルを `tests/` 以下に 1 つ以上持たなければならない。(常時)
5.4. `tests/` 以下にファイル名が接尾辞 `_test.gd` のテストスイートが置かれている間、システムはそれを実行対象として発見しなければならない。(状態)

### Requirement 6: CI での実行

**対象**: §5.5 CI ワークフロー

**受け入れ基準**:

6.1. pull request が作成または更新されたとき、システムは `ubuntu-latest` 上で `make test` を実行しなければならない。(イベント)
6.2. `main` ブランチへ push されたとき、システムは `ubuntu-latest` 上で `make test` を実行しなければならない。(イベント)

6.4. システムは、Godot の取得にサードパーティの GitHub Action を使ってはならない。(常時)
6.5. `make test` の終了コードが 0 でない場合、システムは CI のジョブを失敗させなければならない。(異常系)
6.6. Godot のダウンロードに失敗した場合、システムはテストの実行ステップとは別のステップとしてジョブを失敗させなければならない。(異常系)

### Requirement 7: レポートの出力・削除と保存

**対象**: §6.3 レポート / §5.2 実行スクリプト / §5.5 CI ワークフロー

7.2. CI でテストが実行されたとき、システムはテストの成否にかかわらず `reports/` をアーティファクトとしてアップロードしなければならない。(イベント)

## 8. 実現方針(要点のみ)

- **テストフレームワークに gdUnit4 v6.2.0 を採用する**。理由は、自前の最小ランナーで避けられない 2 つの挙動を gdUnit4 が処理するためである。実機で確認した挙動は次のとおり(Godot 4.7.1、2026-08-11 に検証)。
  - `extends SceneTree` のスクリプトにパースエラーがあると、Godot が main シーンへ切り替わって終了しない。gdUnit4 は探索時にパースエラーを検出し、レポートを出力せずに終了する(無限実行にならない)
  - `assert(false)` は関数を中断するが SceneTree は動き続け、終了しない。gdUnit4 は失敗を記録して終了コード 100 を返す
  - 対応版は README の対応表で v4.5〜v4.7.1(gdUnit4 v6.2.0)
- **gdUnit4 をリポジトリへコミットせず、取得スクリプトで再現する**。履歴に 516 ファイル・1.7MB を入れないことを優先した判断であり、オフラインで動かないことと CI で毎回ダウンロードが走ることを引き換えにしている。
- **取得物の照合を `plugin.cfg` の `version` で行い、アーカイブのチェックサムを使わない**。GitHub が自動生成するソースアーカイブは再生成でバイト列が変わりうるため(§3 の未検証の前提)、チェックサムでの照合は将来 CI を壊す要因になる。`plugin.cfg` の照合は、依存している中身そのものを確認する点でも目的に合う。
- **実行スクリプトが gdUnit4 の終了コードを透過し、独自の判定を 1 つだけ足す**。足す判定は「gdUnit4 が 0 を返したのにテストケースが 0 件なら失敗」である。テストを 1 件も実行しないまま緑になる経路と、パースエラーが見逃される経路は、次の 3 通りに分かれ、それぞれ別の規則で失敗として表出する。

  | 経路 | gdUnit4 の終了コード | レポート | 失敗として表出する規則 |
  | ---- | -------------------- | -------- | ---------------------- |
  | パスの指定を誤り、テストスイートを 1 件も発見しない | 0 | 出ない | 件数判定(4.2) |
  | パースエラーを含むスイートだけを対象にした | 105 または 0(割れる。§3) | 出ない | 0 の回は件数判定(4.2・4.6)、105 の回は透過(4.4) |
  | パースエラーを含むスイートが正常なスイートと混在する | 134(クラッシュ。§3) | 出る | 透過(4.4) |

  件数判定が塞ぐのは上 2 つの経路であり、3 つ目はレポートが出るため件数では捕まらない。3 つ目を捕まえるのは「0 以外はそのまま返す」という透過の規則である。件数判定が成立する条件として、実行の前に `reports/` を削除する(§5.2 副作用 3)。連番を蓄積したまま「新規に作られた連番」で判定する形も採れるが、削除する方が判定の規則が 1 文で済み、レポートが 1 回分だけ残るので調査の対象も一意になる。
- **入力のシミュレーションをテストの手段にしない**。gdUnit4 自身が「headless では `InputEvent` がエンジンを通らない」と警告する。この制約は `foot-player`(unit #2)以降の設計に影響するため、記述規約に禁止事項として明記する。
- 本リポジトリは用語集(`docs/glossary.md`)を持たないため、契約の名前は既存コードと Godot・gdUnit4 の語彙に合わせた。
