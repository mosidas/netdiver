# 変異検査の規律

「緑であること」は「欠陥を捕らえられること」を意味しない。実装を壊す変更(変異)を注入しても
緑のままなら、そのテストはその欠陥に対して無力である。**タスク定義を書くとき(dev-decompose)は
各項目が変異で死ぬ形になっているかを実装の要点へ書き、レビューするとき(dev-implement)は
変異注入で実測する。**

出典: unit #3 `foot-enemies`・unit #4 `analysis-ability`。各項目の根拠コミットを併記する。

## 規律

1. **各数値項目は、テストが既定と別の値へ差し替えて渡す。**
   既定値のまま渡すと、実装がその値を直書きしても緑になる。既定値どうしが同値の項目
   (例: 2 つの武器の弾速がどちらも 300.0)はとくに危険で、既定のままだと別項目を渡す変異が
   素通りする。担保はここに置き、grep に置かない(grep は整数のリテラルを捕らえられない)。
   テストが使う値が既定と一致しないことを固定する番人のケースを 1 本置く。(`173fae6`)

2. **分岐は両側にケースを割り当てる。**
   片側だけを観測するテストは、分岐を消す変異を捕らえない。とくに「基底の既定と一致する側だけを
   観測する」形を作らない(真を返す側だけ・偽を返す側だけを見ると「常に同じ値を返す」変異が
   生き残る)。(`2dd8d46`)

3. **「しないこと」を静的な検査だけで示さない。**
   ソースの文字列・正規表現を見る検査は等価な別解を素通りさせる。実測例: 代入を禁じる正規表現は
   `set("<プロパティ名>", ...)` を、同期実行を求める検査は `call_deferred` 化を通した。
   必ず振る舞い側のケースと対にする。(`6d87716`)

4. **同期で駆動するヘルパを使うタスクは、実フレーム(実時間)で駆動するケースを 1 本は持つ。**
   ヘルパが呼び出しの順をテスト側に持つと、実装の中の配線を観測できない。ヘルパだけで組んだ
   スイートは「実装が毎フレームその関数を呼んでいること」を 1 度も見ていないことがある。(`5534916`)

5. **拒否する呼び出しには、成功する呼び出しと別の値を渡す。**
   同じ値だと「状態を変えない」ことが観測できない。あわせて**状態が初期値でないところで拒否させる**
   (残り 0 の状態で拒否を確かめると、状態を 0 へ落とす変異が no-op になって素通りする)。(`2dd8d46`)

6. **境界を厳密比較するガードには「境界のすぐ外」の値を 1 つ置く。**
   置かないと述語がしきい値へ緩む変異(`<= 1` を `< 2` へ、`>=` を `>` へ)を捕らえられない。
   境界をフレーム数・回数で数えるときは、**判定の境界を跨ぐ長さの列**を与える。境界の内側に
   収まる短い列だけでは、判定そのものを消す変異でも同じ結果になる。(`384a8b4`・`7593936`)

7. **等価変異をテストで固定しようとしない。**
   到達しない防御・ガードの順序・振る舞いが完全に同じ書き換えは、原理的に落とせない。
   見つけたら記録だけして対処しない。無理に固定しようとすると、要求の外の実装を縛る。(`cbbee70`)

## unit #4 で足された 2 件

8. **参照先の中身を見ない検査は、参照を差し替える誤りを検出しない。**
   「設定されていること」「名前が許可集合に入ること」だけを見る検査は、参照先を別のものへ
   差し替える変異を通す。**参照を解決して型・内容まで見るケース**を対に置く。実測では、
   参照を解決してルートの型を見る 1 ケースだけがこの変異を落とした。(`d91684a` → `0ffbb81`)

9. **同種の複数インスタンスを繋ぐ宣言は、「解決した先が当のインスタンス自身であること」まで見る。**
   種別が違えば他の検査が取り違えを偶然拾うが、同種 2 つでは「両方が同じ相手を指す」誤りを
   この 1 点でしか落とせない。(`f6b580e`)

## レビューの手順

- レビュアーは**変異を実際に注入して実測する**(読んで判断しない)。1 タスクあたり 10〜25 種を目安に、
  上の各項目に対応する変異を作る。生存した変異は、等価変異か・要件中立か・検出力の欠陥かを判定し、
  欠陥なら塞ぐケースを要求する。
- **復元に破壊的な git 操作を使わない。** `cp` で退避 → 書き換え → 退避ファイルから `cp` で復元し、
  作業ツリーが元に戻ったことを確認する。
- **生存した変異を「対処しない」と決めたら、変異の内容と理由を記録に残す。** 次の作業単位が
  同じ箇所へ手を入れるときの前提になる。
- 検出力の欠陥が次のサブタスクでしか塞げない場合は、**必須の宿題として申し送る**。実測例:
  「呼び出しを凍結する」変異が 136 ケース緑のまま生存し、次のサブタスクの両側のケースが
  初めて落とした。(`5534916` → `6d87716`)

## 担当範囲の規律(検出力と表裏)

- **担当外の要件を先回りして実装しない。** 無検証の分岐が実装に残り、かつ後続タスクが RED から
  入れなくなる(レビューで差し戻しになった実例がある)。
- **要件の割り当てに矛盾を見つけたら、黙って解消せず申告する。** 実測では、分解時の要件の
  割り当ての誤りが、実装者の申告によって初めて捕らえられた。
